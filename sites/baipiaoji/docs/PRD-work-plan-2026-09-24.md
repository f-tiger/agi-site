# PRD：按岗位算 AI 方案（/work-plan）

2026-09-24｜owner 原话：「大模型每个月都在迭代，配套的 jev、muse 等新模型层出不穷，但是如何转换为 AI 赚钱工具……对各行各业的人是很困难的，因为他们要改变自己的工作习惯。最好是构建一个站点，可以让更多人根据自己的实际工作，构建一个 AI 工具，它可以自动化计算，然后推荐 AI 的一整套解决方案；因为很多方案是收费的，作为试用免费，高阶的可以对这个给用户工具进行收费。」

按仓库固定流程：需求调研 → 洞察 → PRD → 上线。

## 一、需求调研（一手在前）

| 面 | 读数 | 读法 |

| 你能白嫖什么 `/free-for-you` | 6 pv | 同上 |

**外部**

- 竞品：[There's An AI For That](https://theresanaiforthat.com/task/work/) 按岗位 / 任务列 4 万+ 工具，只给清单；[agentarius.ai](https://agentarius.ai/) 20 个岗位、150 个工具、带免费档标识与核对日期，**明确不做任何计算**；中文侧是知乎式清单与导航站。

## 二、洞察

- 「按岗位推荐 AI 工具」这一格已经挤满，而且全是清单。**没人回答的是：这一套免费额度，够不够我这份工作的量。** 回答它需要逐家核实过的、带单位的免费上限——本站恰好有（109 条结构化配额、带官方来源与核实日期）。
- 读者要改变工作习惯，第一个障碍不是「不知道有哪些工具」，而是「不知道用免费的能不能撑住、撑不住要花多少」。所以这个页面的产出是一个**判定**，不是一张清单。
- 付费：前端计算锁不住（09-16 裁定：view-source 可绕过的东西不会被付费），能卖的只有服务端持有的东西。本站已有的会员正好卖这个（云端工作区 + 版本历史），不新建收款面。

## 三、PRD

**定位**：选岗位、填工作量 → 每个任务按步骤给工具 → 把同单位的官方免费上限加起来与工作量比较 → 够 / 不够 / 说不准 / 官方未公布。

**硬规则**
1. 额度数字只从 `data/*-quotas.json` 构建期读取；`work-roles.json` 只放编辑字段（闸门断言：出现任何非编辑键即红）。
2. 只给「产出的正是任务计量的那种东西」的工具写容量规则；流水线上的其它工序（抠图、放大、排版）不进加总。
3. 有官方数字的工具不够、但同一任务里还有官方未公布上限的工具 → 判「说不准」，不判「不够」。
4. 保守取值：可灵按官方付费单价折算（3 条 / 天），不用官方自述的旧口径（6 条）；GitHub Models 取高档模型的 50 次 / 天。
5. 不算「能省几小时」，不带推广 / 返利链接；约束（国内直连 / 商用）只按 tags 与 `licence.json` 判定，未标注的如实写「未标注」。

**MVP（本轮上线）**
- `/work-plan` 中英两页：12 个岗位、21 类任务、65 款工具，其中 19 款有同单位官方数字参与计算；无 JS 也可读的 12 张岗位静态表；5 条 FAQ（可见文本与 FAQPage JSON-LD 同源）；WebApplication JSON-LD。
- 免费：计算、复制 Markdown、下载 JSON。
- 会员：「保存到云端」走 `tools/member-studio` 的同源 postMessage 协议；`catalog.mjs` 新增 `externalProducts`（ai-work-plan），会员服务端 `allowedProduct` 与会员页产品清单都认它。
- 入口：中英首页 hero、栈组装器、站内搜索、llms.txt。**不进全站 rail / 页脚**（每页都带的元素一改就全站 lastmod 刷新）。
- 仪器：`calc` 事件 `/plan/<岗位>/<任务数>[+cn][+biz]`、`/plan-save/<岗位>`、`/plan-export/json`（均在 hit.js 白名单内，闸门断言）。

**不做**
- 新站 / 新子域（受众与 bpj 相同，数据在 bpj）。
- 新收款面、前端付费墙、注册门（工具注册门的判定线 09-26 还没结算）。
- 按岗位批量生成 SEO 页（本站 08-21 那批判定页 27 天 0 读者；先看这一页有没有人用）。
- 给 Muse / Jev 这类新模型建页：它们要先过本站的核实流水线进入 tools.json，才会出现在方案里。

**验收**
- `scripts/test-work-plan.mjs`（push 路径）：容量规则全部能读出数、无死规则、保守取值、加总逻辑 7 种情形；变异测试三种都红（手写额度进 roles 文件 / 配额字段改名 / 月度折算写错）。
- `--dist`：静态表 12 张、FAQ = JSON-LD、嵌入数据完整、脚本能解析、hreflang 成对、sitemap 收录。
- 浏览器（本地 Chromium，390 px）：中英两页选岗位 → 计算 → 改量 + 约束；零页面错误、零横向溢出；保存到会员工作区 → 从工作区恢复，数值逐字一致。
- 部署后自检：两页在线带计算器；线上会员产品清单含 ai-work-plan。

## 四、判定线（已进 `data/fleet-bets.json`）

- `bpj-work-plan-use-1024`：30 天内 `/plan/%` 计算 ≥20 次（按日 × 国家 × 路径去重）且两页真人 pv ≥60 → 按 D1 里的岗位分布加岗位与容量规则；<5 次 → 只维护，不再加岗位。
- `bpj-work-plan-paid-1124`：60 天内出现 ≥1 笔已付会员且其工作区里有 ai-work-plan → 付费层有第一个买家；已付 0 且 `/plan-save/` <5 次 → 不再给这个规划器加任何付费功能；保存点击 ≥5 但已付 0 → 卡点在支付方式（目前只有 USDT），属 owner 的 Stripe 决定。

## 五、诚实的预期

本站带来源的真人约 14 / 天，已建的付费层 5 天 0 个买家。这个页面把「按岗位 + 算得清」这一格补上了，但**它不会自己带来流量，也大概率不会在第一个月产生付费**。它存在的理由是：这是本站数据唯一能回答、而清单型竞品回答不了的问题；以及它用的是已经建好的付费通道，不增加新的维护面。
