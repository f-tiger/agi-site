# 部署架构：为什么最后**不**迁移（2026-08-16 实测结论）

**由来**：账号 GitHub Actions 额度 15 天用掉 90%（1803/2000，9-1 重置）。诊断出本仓
是最大消耗源（8-15 单日 22 次运行）。owner：「那直接学 agi 啊，明显 agi 更加合理」。

## 先说结论

**不迁移。** 方向（少花 Actions）是对的，但实测数据显示迁移会让情况更差 6.6 倍。
真正有效的是砍掉每次 push 的无用步骤——已完成，效果如下。

## 实测对照

| 方案 | 每次 push 成本 | 月度额度 | 可支持推送数 |
|---|---|---|---|
| 修复前 Actions | 3.5–8 分 | 2000 分 | ~350–570 次 |
| **修复后 Actions** | **0.6 分**（实测 run 31928679623） | 2000 分 | **~3300 次** |
| 迁 Cloudflare Pages Git | 1 次构建 | **500 次/月**（[官方 limits](https://developers.cloudflare.com/pages/platform/limits/)） | **500 次** |

迁移的隐含假设是「Cloudflare 构建不要钱」——**错的**，Pages 免费版是 500 次/月硬顶。

## 「提交产物」这条路:我原先的反对理由是错的(2026-08-16 实测更正)

原文写「每次数据变动会重写 1540 个文件、按 60MB 量级入库,几个月膨胀到 GB 级」。
**这是没实测就下的结论,实测差了几个数量级**:

| 测项 | 原先声称 | 实测 |
|---|---|---|
| dist 压缩后(git 存压缩包) | ~60MB | **18.7MB**,且是一次性 |
| 3 个工具更新核实日期 → dist 变动 | 「重写上千文件」 | **0 个文件** |
| 1 个工具改一句文案 → dist 变动 | 同上 | **7 个文件**(工具页+分类页+对比页,中英各一) |
| 近期日常数据提交 | — | **1 个文件、30 行增删** |

`build.mjs` 是确定性的——数据不变则输出逐字节一致(它自己打印 `0/1280 页内容有变化`)。
git 只存真正变动的增量。所以「提交产物」在体积上**完全可行**,一次性 18.7MB 打底,
之后每天几个到几十个文件。

**但仍然不做**,理由与体积无关:见上表——修复后每次 push 只花 0.6 分钟,2000 分钟
够 ~3300 次推送。改架构是在解决一个已经不存在的问题,还要搭上 owner 的后台操作。

（agi 之所以是「产物即源码」,是因为它的 191 个页面本来就是手写的,没有生成步骤——
那是它的自然形态,不是一个可以照搬的优化。）

## 实际做了什么（已生效）

1. `concurrency.cancel-in-progress: true` —— 连续快推只有最后一次真部署。
2. **28 步 → 17 步**：IndexNow 推送、Wayback 存档、RSS 聚合器、域名/DNS 校验、
   爬虫探针、D1 快照导出等「每日维护 + 外部副作用」只在定时任务跑。
   （8-15 那天等于给 IndexNow 推了 22 次、往 Wayback 存了 22 次，已接近滥用外部服务。）
   保留在 push 路径的是：正确性校验 + 构建 + 部署 + 部署后 7 个自检。
3. 删除 `Ensure Pages project exists`——项目早已存在，却要为它完整下载一次 wrangler。

**验证**（run 31928679623，f9aa770）：Deploy 步骤 20 秒成功、7 个自检全过、
11 个维护步骤按设计跳过，总计 35 秒。部署与验证能力一点没少。

## 仍然成立的一条

改造解决「每次 push 的成本」，不解决「一天推 22 次」本身。会话内应把多次改动
合并成一次 push——这条对 agi、白嫖计同样适用。
