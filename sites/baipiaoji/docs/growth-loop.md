# 增长闭环：每两天自动跑一次

目标是让日均流量持续往上走。核心思路：**把「用户实际怎么用这个站」变成「站该怎么改」，中间不需要人。**

运行方式：GitHub Actions 每两天北京时间 09:00 自动执行，也可在 Actions 页手动触发。

---

## 它每次做什么

```
GA4 取数（近 14 天）
   ↓
自动优化（可逆、无需判断的部分）
   ├─ 按真实点击重排各分类的推荐位
   └─ 把真实搜索词回填进方案关键词
   ↓
产出选题待办（data/backlog.json）
   └─ 来源：search_no_result —— 用户搜了但站内没有的
   ↓
出报告（docs/growth-report.md）
   └─ 趋势 / 赢家页面 / 出站点击分布 / 需要人做的事
   ↓
提交 → 重建 → 部署
```

## 自动执行 vs. 交给人：边界在哪

这条线上最危险的事，是让自动化去改内容。本站唯一别人抄不动的东西是「每条福利都核实过」——一旦自动化开始生成没核实的内容，这个差异化就没了。所以边界划得很死：

| 自动执行 | 交给人 |
|---|---|
| ✅ 按点击数据重排推荐位 | ❌ 增删工具 |
| ✅ 回填搜索词到关键词 | ❌ 写方案正文 |
| ✅ 关闭已被覆盖的选题待办 | ❌ 修改福利描述 |
| ✅ 生成报告与待办清单 | ❌ 发布任何未核实的内容 |

自动改动都是**可逆**的（改的是排序和关键词，不是事实），出问题 `git revert` 一次即可。

另外有两条防噪声的闸门：

- **单分类 14 天点击不足 20 次时，不动推荐位**——样本太小，跟着噪声走会越调越差。
- **搜索词被搜不足 3 次、或长度不在 2–12 字之间，不回填**——避免把长句和误输入塞进关键词。

被跳过的项目会**明写在报告里**，不静默略过——否则你会误以为"跑过了没问题"。

## 开启 GA4 取数（一次性，约 10 分钟）

没配也能跑，但只有站内信号，自动优化不会触发。配完才是完整闭环。

**只有前两步需要你本人操作**（要 Google 账号），第三步之后交给脚本。

> 📌 **为什么还要配这个——我不是已经能读 GA4 了吗？**
> 会话里的我可以通过 **Supermetrics MCP** 读 GA4（`docs/ga4-baseline.md` 的数据就是这么取的），
> 但 **MCP 只在对话里可用，跑不进 GitHub Actions**。增长闭环要每两天无人值守地自动运行，
> 必须有自己的凭据。两条路互相不能替代。

### 1. 建服务账号（你做）

1. 打开 [Google Cloud Console](https://console.cloud.google.com/) → 新建或选一个项目
2. 启用**两个** API：**Google Analytics Data API**（读数据）和 **Google Analytics Admin API**（建维度）
3. 「IAM 与管理 → 服务账号」→ 创建服务账号 → 「密钥 → 添加密钥 → JSON」下载

> 下载的必须是**服务账号密钥**（JSON 里有 `client_email` 和 `private_key`），
> 不是 OAuth 客户端配置。贴错了脚本会直接告诉你。

### 2. 给它 GA4 权限（你做）

GA4 后台 → 管理 → 媒体资源访问管理 → 添加用户 → 填服务账号邮箱（`xxx@xxx.iam.gserviceaccount.com`）：

| 你想要 | 角色 |
|---|---|
| 只让闭环读数据（自定义维度自己手动建） | **查看者** |
| 让脚本自动把 8 个自定义维度建好 | **编辑者** ← 推荐 |

### 3. 填两个仓库 Secret（你做）

GitHub 仓库 → Settings → Secrets and variables → Actions → New repository secret：

| Secret | 值 |
|---|---|
| `GA4_PROPERTY_ID` | **`547077892`** —— 已经查到了，直接填这个。（它是 baipiaoji.com 的 GA4 媒体资源 ID，纯数字；**不是** `G-` 开头的衡量 ID） |
| `GA4_SERVICE_ACCOUNT_JSON` | 刚下载的 JSON **全文**原样粘贴，不要手工改换行 |

### 4. 点一下验收（脚本做）

Actions → **GA4 setup** → Run workflow：

- `mode = check` —— 只体检：凭据对不对、权限够不够、缺哪几个维度、能不能真的取到数
- `mode = apply` —— 顺手把缺的自定义维度全建了（需要「编辑者」）

报告直接打在 Actions 的 Summary 里，**每个报错都附带具体怎么修**（填成衡量 ID 了、私钥换行坏了、API 没启用、权限是查看者……）。

本地也能跑：

```bash
GA4_PROPERTY_ID=123456789 GA4_SERVICE_ACCOUNT_JSON="$(cat key.json)" npm run ga4:check   # 只体检
GA4_PROPERTY_ID=123456789 GA4_SERVICE_ACCOUNT_JSON="$(cat key.json)" npm run ga4:setup   # 体检 + 建维度
```

### 脚本会建这 8 个自定义维度（事件范围）

| 参数名 | 没有它，闭环里哪一段会瞎 |
|---|---|
| `search_term` | 选题积压——用户搜了但站内没有的关键词，最高质量的选题来源 |
| `tool_name` | 出站点击，离营收最近的信号 |
| `tool_category` | 按真实点击重排各分类推荐位 |
| `placement` | 分辨从工具卡 / 详情页 / 方案步骤 / 作业步骤点走 |
| `plan` | 方案完成率（点击 ≠ 做成） |
| `hustle` | 四层阶梯通不通：作业带得动方案吗 |
| `site_edition` | 中英文分别贡献多少流量，决定英文版还要不要投入 |
| `step_no` | 卡在第几步——全站颗粒度最细的改进信号 |

> ⚠️ 自定义维度只对**创建之后**的数据生效，历史数据不会补。所以越早建越好。

## 报告怎么看

每次运行后读 `docs/growth-report.md`，关心这几块：

1. **「需要人做的」** —— 按优先级排好了，从上往下做
2. **「选题积压」** —— 用户搜了但站内没有的关键词，按需求量排序。**这是最高质量的选题来源**：不用猜用户想要什么，他们已经打字告诉你了
3. **「方案完成度」** —— 用户在方案页底部自评"搞定了 / 卡住了"。**点击 ≠ 做成**：完成率低于 50% 说明步骤本身有问题，不是流量问题——这种情况加流量没用，得重写这套方案
4. **「卡点分布」** —— 用户点了"卡在第几步"。这是全站颗粒度最细的改进信号：**直接告诉你该重写哪一段，不用猜**
5. **「出站点击按位置分布」** —— 若 `plan_step`（方案步骤里的链接）点击率高于 `card`（工具卡），说明"方案→工具"这条路径成立，应该多写方案；反之说明用户更爱直接逛工具库，应该多补工具

## 2026-08-04（第二轮）：出站网络被策略封禁，本轮不写任何新数字

D1 读数正常，7 日累计约 115 次浏览，集中度极高：

| 页面 | 7 日浏览 |
|---|---|
| `/en/c/coding` | 45 |
| `/`（中文首页） | 17 |
| `/en/` | 15 |
| `/en/myths`、`/myths` | 各 5 |

`/en/c/coding` 一页占了近 40%——英文 coding 类目是目前唯一称得上"引擎"的入口，其余都是涓流。

**本轮遇到的硬约束**：运行环境的出站网络被收紧为白名单，除 `api.github.com` 外
所有厂商官网（capcut.com、microsoft.com、huggingface.co、mistral.ai、cohere.com、x.ai、
open-webui.com、bigmodel.cn 等，实测 18 个域全部 `connect_rejected` 403）均不可达，
WebFetch 与 curl 同时失败。

据此，本轮**没有新增任何一条 limits**。三条边界必须说清楚：

1. 查不到官方页 ≠ 官方没有官方页。这次是我们自己的网络被拦，
   若据此把 ms-copilot、剪映、跃问写进"查无官方来源"清单，等于把环境故障伪装成对厂商的判断——
   那是往站上写假话。宁可这一格空着。
2. 搜索引擎仍可用，但返回的是 CSDN、知乎、腾讯云社区等第三方转述。
   第三方口径一致 ≠ 官方口径（这正是 siliconflow 被列入拒绝清单的原因），一律不采信。
3. 已有的 108 条 limits 全部不动。

**因此本轮改做不依赖取数的放大动作**：把"拒绝"从单独页面搬到流量真正落地的分类页。

- 分类页对比表下方新增"这几个为什么不在表里"，直接列出该类目的拒绝条目与理由；
- 页头新增覆盖率一行（可跳转到表格）：**有官方数字的 + 明说查不到的 = 有交代的**。

结果是三个类目达到 100% 有交代——coding 19/19、image 17/17、study 6/6。
其中 coding 正是访问量第一的页面：读者第一眼看到的不再是"收录了 19 个工具"，
而是"19 个里 18 个有官方数字，剩下 1 个我们明说查不到"。
别的站是"没写"，这里是"写了为什么没写"——这句话只有把拒绝摆在同一页才成立。

**下一轮的前置条件**：出站网络恢复后，按流量优先级补 limits——
`ms-copilot`、`yuewen`（chat）、`jianying`（video）三个都已有真实访问却仍是空白，排在最前。

### 同一轮的第二个动作：补上「对比页」这个缺失的入口

上一节的结论是"流量集中在 /en/c/coding 单页"。调研之后发现这不是巧合：
这个赛道排在搜索前面的页面**几乎全是「X vs Y」页**——
Cursor vs Windsurf、Copilot vs Cursor、Cursor vs Claude Code……而本站一条对比页都没有。
只有类目入口、没有对比入口，等于把最大的一股搜索意图挡在门外。

同时看到一件更有价值的事：那些排在前面的对比文章**不给出处**。
搜索结果里仍在流传 "GitHub Copilot Free: 2,000 completions and 50 agent requests per month"
这类数字，而本站 cursor 条目在 08-03 核实时已经写明：这套数字来自旧定价结构、现行官方页面不再公布，
因此我们不复述。**同样的页型，别人给的是拍脑袋的结论，我们给的是两边的官方原文 + 出处 + 核实日期。**

于是新增 `/vs/`：158 组对比 × 2 语言 = 316 页，全部由已核实数据生成，**零新增核实成本**。

硬门槛（宁可少几页，不做空壳页）：
- 两边都必须 quota / wall / source / checked 四项齐全；
- quota ≥ 40 字、wall ≥ 25 字，保证每页都有实质内容；
- 英文侧必须有独立的 en 覆盖，否则不生成——不让中文漏进英文页；
- 只在同类目内、且至少一方是 hot 的工具之间配对，避免生成没人搜的组合。

页面不下结论，只并排放两边的官方口径 + 出处 + 核实日期，再接该类目的"先问什么"规则。
"谁更好"取决于读者要干什么，"官方怎么说"不取决于任何人。

入口也补齐了——对比页必须能从站内走到，否则等于没上线：
侧栏导航、每个工具页的"和谁比"、每个分类页的"两两对照"，三处反向链接 + sitemap（318 条）+ IndexNow 自动提交。

**顺带修掉一个活了很久的渲染 bug**：数据里用 `**…**` 标重点，但 limits / myths / 方案步骤 /
旅行条目等多处渲染时只做了转义、没转 `<strong>`，星号原样出现在页面和搜索摘要里——
波及 43 个工具页在内的一批页面。现已全部改走 `strong()`（HTML）或 `plain()`（schema / meta / llms.txt），
并在 `verify-dist.mjs` 加了 `rawMd` 门禁，漏一处就构建失败。

本轮站点规模：446 → 762 页，构建验证五项全零（broken / ldErr / zhLeak / placeholder / rawMd）。

### 分发管道体检（2026-08-05）：全绿，但两处在做无用功

从 CI 日志逐条核对了每天实际在跑的分发动作，结果是全部成功——
IndexNow **HTTP 200、提交 762 条**，Wayback 5 页全存档，Ping-O-Matic pinged，
信标自测 204，域名与 DNS 已绑定。第一方打点链路和部署链路都没有问题。

但里面有两处在做无用功，改掉了：

**一、IndexNow 每天整站重推。** 协议的本意是「告诉我们哪些页变了」，
每天把全站 762 条原样推一遍，等于每天说一遍「全都变了」——会被降权甚至忽略，
而这偏偏是本站唯一**小时级**（而非周级）的收录通道，Bing 同时是 Copilot 的检索底座，
浪费不起。改为按内容哈希清单比对，只推真正变过的 URL；
清单缺失时才整站提交；提交失败不更新清单，下次自动重推。

**二、Wayback 只存 5 个固定页。** 存档页会被搜索收录、也在多数 AI 检索的抓取范围内，
且永久回链本站——对一个两周新站，这是少数几个能立刻产生外部可引用副本的通道。
但本站最可被引用的资产（160 个对比页、方法论页、拒绝清单）一个都不在那 5 个里。
改为按价值分层取前 70：方法论 → 拒绝清单 → 流言核查 → 首页 → 数据集 → 对比总览 →
类目页（28）→ 对比页（30）。70 这个数是算出来的：不到 40 时类目页会把名额占满，
对比页一个也进不去。

### 关于「快速导流」这个目标，把话说死

自然搜索的收录有物理延迟，不存在当天见效的自动化路径。当前可用的通道只有三条，
全部已在每日运行且已验证成功：IndexNow（Bing/Yandex/Naver，小时级）、
Wayback（存档副本）、Ping-O-Matic（聚合器）。Google 不支持 IndexNow，
只能靠自然抓取或 Search Console 提交，而 GSC 凭据尚未配置。

能让流量当天起量的手段只有三类：投放、往社区/社交发帖、动用已有受众。
三者都需要账号或预算——这与「全自动化、不要我」这个约束直接冲突。
所以本轮之后不再重复承诺"剧烈上升"，只报可核验的两件事：
管道是否在跑（现已逐条验证）、内容是否在变好（覆盖率与页数）。

### SEO 审计（2026-08-05）：两个影响面最大的缺陷，都是自己造成的

调用审计技能对 dist/ 全量 770 页做了技术与页面级体检。robots、canonical、viewport、
og、schema、H1 结构都过关（仅两个 widget iframe 页无 canonical，属设计如此）。
但有两项严重超标，而且其中一项是上一轮「关键词修正」自己造成的：

| 项目 | 修正前 | 修正后 |
|---|---|---|
| title 超 60 字 | 472 / 770（中位 77，最长 147） | 76 / 770（中位 46，最长 88） |
| meta description 超 160 字 | 591 / 768（中位 285，最长 785） | 12 / 768（中位 141） |

**description 是这里真正被低估的一项**。它不只影响搜索结果摘要——
AI 引擎最常整段摘录的就是这段文字。中位 285 字意味着重点被埋在被截断的位置之后。
改为在 `layout()` 里统一截到 155 字并在断句处收尾（中英文标点都认），一处改动覆盖全站。

**title 超长则是上一轮加日期戳加出来的**。把「（2026-08-05 核实）」放进 title 看似增强新鲜度，
实际占掉 13–15 字并把关键词挤出截断线。日期已在 H1 下方、正文与 schema 里各存一份，
title 里那份是纯冗余，删掉。方案页与作业页另有问题：标题是完整问句（最长 135 字），
现在只取第一个断句前的核心短语进 title，完整问句仍作 H1，语义不丢。

剩余 76 个超 70 字的基本是英文对比页（如 Alibaba Cloud Bailian vs Cloudflare Workers AI），
长度来自工具名本身——那正是要检索的关键词，不能砍。

## 趋势雷达（2026-08-08 起）：每日循环的取活入口

每日循环第 1 步（调研）改为**先读 `data/agenda.json`**，再做增量 WebSearch。
雷达由 `scripts/trend-radar.mjs` 每日在 CI 聚合五路站内信号生成：

| 信号 | 来源 | 触发门槛 | 产出行动 |
|---|---|---|---|
| 外部热度 | discovery.json（HN） | ≥40 分已在采集端过滤 | 核实候选 → 入库 |
| 厂商异动 | limits-history.json | 同类目 14 天 ≥2 条变更 | 提前复核整个类目 |
| 内容衰减 | tools.json checked 老化 | >30 天（30 天内不开药） | 复核并刷新日期 |
| 需求缺口 | backlog.json（站内搜索无结果词） | status=todo | 评估成方案/收录 |
| 来源复猎 | no-source.json 按日轮换 | 每天固定 2 条 | 重查官方，查到即撤下拒绝条目 |

分数是领先指标的相对排序，不是预测；队列上限 12 条，门槛之下宁可空手。
雷达只排队不写事实——一切核实动作仍走硬规则（官方来源、limits-edit.mjs 两步写入）。
