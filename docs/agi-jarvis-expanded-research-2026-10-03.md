# 贾维斯：扩展调研与修订方案

调研日期：2026-10-03。Owner 要求先扩大调研再优化方案；原有自主开发、发布与持续迭代授权保留。本文区分外部证据、工程判断、已实现能力与尚待验证的假设。所有实验用合成任务，不公开客户正文、记忆、账户标识或私有统计。

## 决策

长期目标是能够承担持续责任的个人助手。当前原型只是研究任务的起点，不能代表 AGI，也不足以证明客户喜欢。建议先服务一个可反复验收的场景：**持续跟进一个 AI 工作或产品问题，维护证据、变化与下一份可交付成果**。首批用户假设是个人开发者和小团队；真实需求与付费意愿尚未验证。

优先级改为：可靠交付与恢复 → 来源明确的记忆 → 可测量的低成本分工 → 受控工具扩展。将“多做功能”改为“每轮证明一项改动使相同任务更可靠、更省资源或更有用”。

## 三轮优化与两轮反证

1. 目标：把“像 Muse/dots”翻译为可测量结果——用户少重复背景、任务中断可恢复、成果能使用、重要变化能被发现。界面相似度和聊天长度不作为成功指标。
2. 约束：当前沙箱可见 9 CPU，cgroup 内存硬上限 8 GiB，未观察到 GPU；没有已安装的本地推理运行时。生产复用现有 Worker/D1/Workers AI。共享 12 次模型尝试/24 小时窗口与每 IP 窗口 3 次保持不变，失败也计数。瞬时沙箱不充当常驻服务器。
3. 验收：以真实任务结果、证据是否支持结论、恢复后有无重复副作用、实际延迟与实际用量评价。代码夹具只能验证流程；模型质量必须另测。

反证一：即使技术可用，普通 ChatGPT 可能已足够。差异化假设是持续跟踪同一责任、保留经核验的进展并交付具体成果；用复用与主动反馈检验，不靠竞品热度证明。

反证二：小模型、更长记忆和更多代理都可能降低可靠性。采用相同输入与验收条件做对照；发现退步就回退。一次模型成功不称为基准通过，一次失败也不据此否定整个模型家族。

## 优化后的架构

建议分成五个边界明确的部件，逐项建设：

1. **责任与交付物**：目标、完成标准、已有成果、下一步、预算、到期时间。每次执行更新同一个任务，而不是开启无关联聊天。
2. **持久执行器**：状态机、租约、检查点、幂等、暂停/删除及过期清理。模型描述“完成”不能改变这些状态，必须由工具回执或验收决定。
3. **分层记忆**：用户明确偏好；带时间的任务事件；有来源和适用条件的经验。拟加入 `source/type/observedAt/supersedes`，把用户陈述、工具观察、模型推断分开。删除或纠正要能追溯并生效。当前只有可编辑设备记忆与任务记录，不能冒称此完整体系已实现。
4. **按任务分配推理**：算术、筛选、格式与权限用代码；小模型候选做提取、路由和短计划；开放推理候选单独评测。升级由质量门槛与预算决定。失败不通过无限重试或重置配额掩盖。
5. **证据与验收**：工具输出带来源类型和时间。引用 ID 合法只证明引用存在，不能证明结论。后续加入结论与证据片段的对应检查、反例与“不足以判断”样本。

默认单协调器，固定工具契约和按需上下文；公开搜索字段与私有记忆隔离。较重浏览器/桌面能力、外部写入和自改代码留到隔离、回放和结果验证成熟后，不能直接装入共享网页 Worker。

## 本次真实运行带来的修正

第一轮云端合成验收确实调用了模型，但计划未通过格式校验，系统保留资料包并标为受限，没有伪造成功。未保存原始输出，因而不能断言具体是哪一个字段错误。第二轮加入 provider JSON schema、原生对象响应兼容后仍未通过计划校验，输出用满 560 token 上限；尚无原始输出，不能断言截断就是唯一原因。v2 部署及全部发布后检查已通过。v3 进一步取消模型规划调用，由固定代码流程取证，再执行一次短综合；兼容两种响应封装并记录不含正文的格式诊断。实际模型质量仍须单独复测。

首次部署的静态页面和 Worker 已更新，但新增 Cron 注册被拒绝：账户已达到免费 5 个定时器上限。修订方案复用已有两小时维护工作流，不购买升级，不占用新 Cron。页面同步说明后台约两小时检查且可能延迟；通常任务仍在提交后立即执行。维护入口使用专门派生的密钥，一次最多处理一个任务，每轮最多两个，只返回处理数量。

调度资源估算：每天复用现有 12 次作业，新增 0 次作业启动。单次新增步骤最多 4 分钟，配置上界为 48 runner 分钟/天、1,440 分钟/30 天；这是超时上界，非实测日用量。空队列不调用模型；模型总额度不变。需实际观察后再决定是否调整调度，不把资源上界当成可接受的正常消耗。

## 2026-10-04：任务恢复证据与实验

最新有效产品约束为仅限 AGI 本站有效会员；本文早期免费试用建议已由 Owner 后续要求覆盖。扩展阅读 [LangChain 持久化](https://docs.langchain.com/oss/javascript/langgraph/persistence) 与 [AWS 幂等恢复](https://docs.aws.amazon.com/durable-execution/patterns/best-practices/idempotency/) 后，本轮选择修复已复现的检查点丢失，而非增加模型或记忆长度。反证：检查点不保证外部调用恰好一次；未保存的读取可以重做，结果未知的模型调用不能默默重试。

先冻结五个恢复案例，旧实现 0/5，新实现 5/5；另增加检索中暂停、模型调用中暂停两项故障注入测试。共 56 项工程测试通过，不是此前规划的 24 项模型质量留出评测。确定性状态机适合本缺陷；现有 8B 与更强 70B 候选的语义质量对照仍未执行。详见 [本轮实现、反证和验收记录](agi-jarvis-recovery-2026-10-04.md)。

## 2026-10-05：Google 注册入口的任务接续

新增核对 [Google OAuth 安全建议](https://developers.google.com/identity/protocols/oauth2/resources/best-practices) 与 [Cloudflare Workers AI JSON Mode](https://developers.cloudflare.com/workers-ai/features/json-mode/)：OAuth `state`/PKCE 负责回调安全，Jarvis 私有任务接续仍应是独立、同标签页、短时的确定性能力交接；Cloudflare 同时明确 JSON Schema 不能保证模型必定合规。因此账号接续不能交给 8B 或更强模型推断。

源码审计发现单独添加的 Google 账号入口没有调用现有接续函数，可能让已完成访客试用的人登录后进入空的新工作区。反证是主要的私钥注册路径一直通过，故已有成功测试没有覆盖所有注册入口。本轮冻结“直接 Google 入口保存最小交接回执、服务端适配器原样保留能力头、错误账号仍不能迁移”实验并修复；未改变模型、额度或调度。详情见 [v10 接续记录](agi-jarvis-registration-continuity-2026-10-05.md)。

## 2026-10-06：由报告进入下一次真实尝试

新增核对 [OpenAI Agents SDK 的 human-in-the-loop 指南](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)：官方实现允许暂停的运行在下一次模型调用前加入新的用户输入，并强调序列化状态本身不认证用户，浏览器端只能持有经授权的展示信息，完整状态、所有权与防重放检查应留在服务端。这支持“先让用户补充实际观察，再继续”，不支持把模型建议静默当成已完成事实或把客户端快照当授权。

反证：多一个接续按钮可能只是增加界面复杂度；把模型生成的下一步自动塞进新任务，也可能放大错误建议。故本轮没有自动提交、自动勾选记忆或自动执行工具，而是用确定性代码生成可编辑草稿，明确保留“我实际尝试了什么、观察到什么”空位，清空记忆、公开搜索与云端同意，只有用户重新确认后才创建任务。报告文本仍按纯文本显示并限制在 1,200 字符内。

候选比较：确定性模板消耗 0 次模型调用；1B/3B 小模型仍会占用共享尝试且可能改写完成标准；现有 8B 更适合有来源的综合，不需要用于拼接已知字段；70B 候选在 [Cloudflare 2026-10-06 官方价格表](https://developers.cloudflare.com/workers-ai/platform/pricing/) 中每百万输入/输出 token 分别为 0.293/2.253 美元，快版 8B 为 0.045/0.384 美元，当前没有质量证据支持为本步骤增加约 6.5 倍输入单价或约 5.9 倍输出单价。价格不是质量结论，后续模型对照仍须使用冻结任务集。

可证伪实验：在中英文已完成任务上点击某条“下一步”，应同时满足（1）草稿包含原目标、所选动作、完成标准和空白实际观察；（2）点击时 D1 新任务数与模型调用数均不变；（3）记忆、公开搜索、执行周期与云端同意回到安全默认；（4）只有注册后的用户重新同意提交才新增任务；（5）控制字符、超长或类 HTML 文本保持纯文本且不越界。固定、无正文的 `jarvis_followup_prepare` 与 `jarvis_followup_start` 只用于统计这条路径的聚合使用，不能当作独立用户、现实任务完成或留存。

## 2026-10-06：负面反馈进入可审阅的纠错恢复

新增核对 [LangGraph 官方 interrupts 文档](https://docs.langchain.com/oss/javascript/langgraph/interrupts) 及其[人机协作实现](https://github.com/langchain-ai/langgraphjs/blob/main/docs/docs/agents/human-in-the-loop.md)：持久检查点可以暂停并等待人的反馈，恢复值可用于审阅和编辑模型输出。官方同时说明恢复会从所在节点开头重新执行，因此中断前的副作用可能再次发生。这支持“先形成可编辑纠错输入，再重新提交”，也反对把负面反馈直接绑定到自动重试。

反证：增加失败原因选项会增加界面复杂度；四个固定分类也不可能覆盖全部失败原因。故分类保持可选、无自由文本，并保留“其他原因”；选择原因只更新该任务的固定反馈值。纠错按钮用确定性代码生成可编辑草稿，清空记忆、公开搜索、周期和云端同意，在用户重新确认前不创建任务、不执行工具、不调用模型。

候选比较：直接重跑现有 8B 可能重复相同错误并消耗共享额度；更强模型仍没有冻结集质量优势证据；让模型解释自身失败会引入自评偏差。固定分类加用户补充字段消耗 0 次模型调用，且能区分来源不足、偏离目标、行动不可执行和其他原因，因此先验证此路径。

可证伪实验：在中英文报告点击“还没有”，选择固定失败原因并准备纠错，应同时满足（1）原因刷新后仍保存在原任务；（2）纠错草稿包含原目标、固定原因、空白修改要求与有用证据标准；（3）准备时 D1 任务数与模型调用数不变；（4）记忆、联网、周期和云端同意复位；（5）游客不能借此绕过一次试用，注册用户也必须再次同意提交；（6）恶意目标保持纯文本且总长不超过 1,200。固定事件只能描述准备/启动路径，不能证明客户、留存或任务成功。
