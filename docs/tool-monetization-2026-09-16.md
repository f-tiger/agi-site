# 工具的付费能力:先量自己,再谈收费(2026-09-16)

owner 原话:「先优化prompt再执行:从工具角度看，哪些工具最容易被付费？然后看看调研做到子站点」。

本文回答两问:①**哪一类工具最容易被付费**(框架 + 外部证据 + 舰队自查);②**要不要为它开子站点**(裁定:不开,
理由与替代动作在 §五)。所有第一方数字为 **2026-09-16 D1 现查**,SQL 写在 §一末尾,任何后续会话可复算。

---

## 〇、三轮 prompt(按 owner 要求先优化再执行)

**第一轮(字面)**:「哪些工具最容易被付费?」→ 会得到一张品类清单(PDF 工具、报税、SEO、图片处理……)。
这张清单**没有决策价值**:品类的付费率是别人站上的读数,搬到一个每天几十个真人的站上仍然是 0。
08-31「零读者不装转化件」和 09-14「按流量计价的通道在此体量都是 €0–5/月」已经把这条路走过两遍。

**第二轮(把问题换成可判定的)**:付费不是**工具品类**的属性,是**使用那一刻**的属性。同一个「计算器」,
放在「今晚要交的申报表」旁边有人付钱,放在「随便算算」旁边没人付钱。所以要问的是:
**这一次使用,是谁在什么压力下、花谁的钱、为了交出什么东西?** 由此得到五个触发器与一条否决门(§二)。

**第三轮(可执行,带舰队约束)**:在回答「哪类工具能收费」之前,**先量舰队自己的工具面到底有没有人用**。
若使用量本身趋近于 0,那么「选哪个工具收费」就是个假问题——这正是本轮的读数结论(§一:28 天 **61 次**)。
因此本轮的产出定为:**框架 + 自查 + 裁定 + 把「工具值不值得做」这件事变成一条会到期的判定线**,
而不是再建一个页面或一个站。

## 二、框架:付费的五个触发器 + 一条否决门

一个工具**容易被付费**,不取决于它多聪明,取决于使用那一刻是否踩中下面的触发器。**踩中 0–1 条的,
永远不要在上面装收款**(这正是舰队 53 张工具页里绝大多数的位置)。

| # | 触发器 | 判据(一句话) | 例子 |
|---|---|---|---|
| ① | **交付物** | 输出是**别人要求**的文件/证明,不是屏幕上的一个数 | 报税申报、合规报告、可提交的表格 |
| ② | **期限** | 有外部截止日,错过要罚钱或失权 | 申报期、保修期、退货窗口 |
| ③ | **别人的钱包** | 买单的是公司/可报销,不是消费者的可选支出 | 卖家工具、开发者工具 |
| ④ | **持续状态** | 价值随时间累积:监控、告警、留痕;一次算完就归零的不算 | 价格/额度变更告警、召回雷达 |
| ⑤ | **责任转移** | 算错要赔或要复核,买的是背书不是算术 | 关税/合规口径、带出处的核算 |

**否决门(先过这一关再谈触发器)**:**这件事能不能被 ChatGPT 一句话答完,或者 view-source 之后自己跑?**
能 → 永远不会被付费。舰队的工具**全部是「不上传的纯前端工具」**(这是新站流水线的硬规定,也是隐私上的优点):
前端工具的逻辑对任何人都是公开的,**结构上就没有可收费的东西**。能收费的只能是**服务端持有的东西**:
数据、时间序列、告警、可交付文件、责任承诺。

**AI 时代把否决门抬高了**(外部证据见 §三):简单计算/换算/判定类的需求正在被助手直接吃掉,
零点击率上升、AI Overviews 覆盖面扩大,而这些工具的价值恰恰是「省一次搜索」。
**结论:纯前端判定型小工具在 2026 年是内容与引用资产,不是营收资产。**

## 五、子站点裁定:不开

按舰队 2026-08-23 的**三条铁律**(缺一不开):

1. **独立技术形态确需隔离?** ✗ —— 收款链路(Stripe Payment Link + webhook + 交付)**SR 已经有一整套**
   (`docs/PACKS-OWNER-SETUP.md`),复用即可,没有任何需要隔离的技术形态。
2. **受众与现有站完全不同?** ✗ —— 会为工具付钱的人,就是 SR 的卖家受众和 bpj 的开发者受众,不是新受众。
3. **自带独立变现闭环?** △ —— 形式上成立(它本来就是为收费而设),但闭环的**入口是流量**,
   而新子域从零权威起步,舰队自己的读数是:六个新站上线 1–2 天,**JS 真人互动 0 次**。

再叠加舰队 09-15 自己写下的两条(`docs/new-site-pipeline.md` §四点五):
- 「**站是最贵的容器**」:一条 workflow、一套闸门、一块每日报数、一个域名。本方向能用**已有站的一页**承载。
- 「10 月四站判定线结算前,再建新站先回答:这个方向能不能用已上线站的一个新页面替代?」→ **能**。

**裁定:不开付费工具子站。** 真要做,做的位置是 **SR 的 `/packs`(已建)** 与 **bpj 的 watch 钩子(已建)**,
而且必须等 §七的判定线给出「有人用」的读数之后。

**同时要对 owner 说清楚的**:这不是「不赚钱」的建议。它是把钱押在**已经有机器每天回访、有卖家受众、
有服务端数据**的两处,而不是押在第 15 个域名上。

## 六、本轮做了什么(可验证,零新增 cron)

1. **六个新站补上「信标真值测试」**(SR 09-13 同款,本轮补齐 after35 / fanzha / codeword / firstjob /
   learn / powerbill):

2. **把六个新站的判定线登记进 `data/fleet-bets.json`**。此前它们只写在各站 CLAUDE.md 里,
   按舰队规矩「**不进台账 = 等于没预登记**」,heartbeat 看不见,到期没人读。本轮补 12 行。

## 七、判定线(预登记,已进台账)

- **`fleet-tool-use-1014`(2026-10-14)**:舰队 28 天「读者主动发起的工具使用」合计(口径 = §一 SQL,
  剔 `__ci`)。**t0 = 61**。
  - **≥120** → 工具面有需求:在使用量最高的那个工具上装**一次意向件**(不是收款,是一个
    「要不要把这个结果做成可下载/可监控的东西」的事件),再按 28 天读数决定值不值得接 Stripe。
  - **<120** → 工具不是营收路径:新站三件套里「不上传的工具」**从必做降为可选**,现有工具只维护不扩建。
- **`fleet-machine-demand-1014`(2026-10-14)**:bpj `/api/*` 与 eco `/mcp` 的调用方里,**剔除本仓 CI
  (curl/8.5.0 等)、`tools/fleet/bot_ua.txt` 里的爬虫、以及自报的 MCP 采集器/索引器**(rokmcp-collector、
  SaSame-MCP-Audit、AIWebIndex…)之后,是否存在真实消费者。**t0:MCP 侧 = 0;`/api/changes` 侧有 1 个
  疑似定时调用方(SG,77 次/26 天)**。

## 十一、单位经济:要多少个「yes」,才有 €100/月

同一个目标(€100/月 ≈ 舰队当前联盟收入的 9 倍),各通道需要的量级差 4 个数量级:

| 通道 | 单价 | 达到 €100/月需要 | 舰队现状 | 差距 |
|---|---|---|---|---|
| 展示广告 | ~$2 RPM | **50 000 pv/月** | 舰队 JS 真人 pv 合计 ≈ 2 800/月 | 18× |
| Amazon 联盟 | €0,085/点击 | **1 176 点击/月** | eco 71/28d | 16× |
| 按次计量 API | £0,10/次 | **~870 次/月** | SR MCP 今天上线,t0 = 0;bpj 机器面 ~400/29d(含自检与索引器) | 2–3×(**唯一同数量级的**) |
| 一次性数据包 $29 | $29/单 | **3,4 单/月** | SR Packs 未开售,0 单 | 需要 ~170 个有买意的访客/月 |
| 订阅 $14/月 | $14/月 | **7 个订阅者** | bpj `watches` 0 行、订阅 6 人(非付费) | 需要 7 个人说 yes |

**这张表改变了第一轮的排序**:按「要多少个 yes」算,**订阅(7 个人)最少**,其次是一次性包(3–4 单),
**展示广告最荒谬**;而**按次计量 API 是唯一一条「现状与目标同数量级」**的通道——因为它的分母不是人,是机器。
但它今天的调用者全是索引器(§一.4),**所以本轮给它的动作是「先上线、先计数」,不是「先收费」**。

## 十二、机器面:舰队唯一在没有推广的情况下每天有第三方回访的面

第一轮的读数(D1 现查):bpj `/api/changes` 394 次/29 天、`/api/mcp/*` ~360 次、eco `/mcp` 105 次/5 天,
**剔掉本仓 CI 后仍有两个独立第三方采集器每天回访**(SaSame-MCP-Audit 23 次/22 天、rokmcp-collector 12 次/12 天)。
对照:SR 的人类面 28 天 **87 pv**、工具使用 **13 次**。

**结论(这就是本轮建东西的理由)**:SR 手上有舰队最「像能收费」的数据(官方关税栈、USITC 候选税号、CPSC 召回),
却只以**没人看的 HTML 页**存在。把它放上机器面,成本是一个 worker 路由,收益是三件可验证的事:
①进 MCP 官方注册表这个货架;②两个已经每天路过舰队的采集器能直接发现它;③**判定线 `fleet-machine-demand-1014`
从此有第二个站的读数**,而不是只靠 bpj 一站。

## 十四、子站的翻转条件(写死,免得下一轮再问一遍)

「不开付费工具子站」不是永久判决,它由三条铁律 + 以下任一条证据翻转:

1. **有人先付钱**:SR Packs 或任何已建收款面出现 **≥3 笔真实付费**(非测试、非退款),说明需求是真的 →
   那时的问题才是「要不要给它一个独立容器」,而不是「要不要建」。
2. **机器面被真实消费**:`fleet-machine-demand-1014` 判 win(非索引器调用方 28 天 ≥20 次且跨 ≥10 天),
   且 SR MCP 28 天调用 ≥870 次 → 计量付费值得单独调研(**向爬虫收费仍然是杀单,这条只针对主动调用的开发者**)。
3. **出现一条有法定死线的交付物**:某个辖区出现「必须提交、错过罚钱」的申报或备案,且一手依据可追(参照 §三 房产税那一行)
   → 这是唯一被证明能让消费者为网页工具付 €35 的形态。

三条都不成立时,默认动作永远是:**把钱押在已建的两处(SR Packs / bpj 变更告警),不建第三处。**
