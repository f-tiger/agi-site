# 优化Prompt（Prompt Optimizer）

在执行任何任务之前，先将用户的原始输入改写为一条结构化的高质量 Prompt，然后按优化后的 Prompt 执行。这样做的原因：用户的原始表述往往省略了目标、上下文、约束和验收标准，直接执行容易做偏方向、返工浪费；先把任务"翻译"成明确的指令，能显著提高一次做对的概率。

## 工作流程

1. **理解意图**：读用户原始输入，判断真实目标是什么、产出物是什么、给谁用。
2. **补全要素**：按下面的清单检查缺失项，能从上下文（对话历史、仓库代码、文件内容）推断的自行补上，不要为可推断的信息打断用户。
3. **输出优化后的 Prompt**：在回复开头用一个引用块或代码块展示优化后的 Prompt，让用户看到你实际执行的是什么。
4. **执行**：严格按优化后的 Prompt 完成任务。
5. **例外**：只有当关键决策无法推断且做错代价高（如删除数据、对外发布、二选一的架构方向）时，才向用户提问。

## 优化清单

将原始输入改写为包含以下要素的 Prompt（缺哪补哪，已明确的不重复）：

- **目标（Goal）**：一句话说清要达成什么，产出物是什么。
- **上下文（Context）**：相关背景——项目、技术栈、目标读者/用户、现状。
- **范围与约束（Constraints）**：做什么、不做什么；语言/框架/风格要求；性能、兼容性、字数等硬性限制。
- **输入（Input）**：要处理的具体材料（文件路径、数据、原文）。
- **输出格式（Output format）**：文件/代码/表格/Markdown？结构和命名有无要求？
- **验收标准（Acceptance criteria）**：怎样算完成——测试通过、可运行、覆盖哪些要点。

## 优化原则

- **忠实**：不改变用户意图，不擅自扩大或缩小需求；补全的假设要在 Prompt 中写明（如"假设目标读者为初学者"），让用户可纠正。
- **具体**：用可验证的表述替换模糊词。"优化一下这段代码" → "在不改变对外接口的前提下，降低该函数的时间复杂度并补充边界条件处理"。
- **精简**：只补对执行有影响的要素，不堆砌模板；简单任务的优化后 Prompt 也应简短。
- **语言一致**：优化后的 Prompt 使用用户所用的语言。

## 示例

**示例 1**
原始输入：`帮我写个脚本处理一下 data.csv`

优化后 Prompt：
> 编写一个 Python 脚本处理项目根目录下的 data.csv：读取全部行，（假设：需要清洗数据）去除空行与重复行，输出为 data_cleaned.csv，保留原始列顺序与表头。脚本需可直接用 `python clean_data.py` 运行，并在结束时打印处理前后的行数。

**示例 2**
原始输入：`这个函数太慢了`

优化后 Prompt：
> 分析 <文件:行号> 处函数的性能瓶颈，说明慢的原因；在不改变函数签名与返回值语义的前提下进行优化，并用现有测试（或补充基准对比）验证优化前后行为一致、耗时下降。

**示例 3**
原始输入：`写篇介绍我们产品的文章`

优化后 Prompt：
> 撰写一篇介绍本产品的中文文章（假设：面向潜在客户的营销场景），800–1200 字，结构为：痛点引入 → 产品核心能力（从仓库 README 提取）→ 典型使用场景 → 行动号召。语气专业但不生硬，输出为 Markdown 文件。

## 不适用的情况

以下情况直接回答即可，不必走优化流程：

- 纯知识问答或闲聊（"什么是闭包？"）。
- 用户输入已经是一条明确、完整的指令，优化不会带来增量。
- 用户对上一轮结果的简短跟进（"把标题改短一点"）——此时沿用已有上下文即可。
